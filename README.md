# 🧠 Mini NPU Simulator

> Codyssey E1-3 「AI가 계산하는 방식을 흉내 내는 작은 계산기 만들기」 미션 결과물

십자가(+)와 X 모양을 **숫자 배열(필터)** 로 정의하고, 입력 패턴과 필터를 **MAC(Multiply-Accumulate: 같은 위치끼리 곱해서 모두 더하기)** 연산으로 비교해 어떤 모양인지 판정하는 콘솔 프로그램입니다.
NumPy 같은 외부 라이브러리 없이 **파이썬 반복문으로 직접** MAC 을 구현했습니다.

## 1. 실행 방법

```bash
python3 --version      # Python 3.8 이상
python3 main.py
```

실행하면 모드를 고릅니다.

| 입력 | 모드 | 하는 일 |
|---|---|---|
| `1` | 사용자 입력 (3×3) | 필터 A, B 와 패턴을 한 줄씩 입력 → 저장 확인 → MAC 점수 / 연산 시간 / 판정(A·B·판정 불가) → 3×3 성능 표 |
| `2` | data.json 분석 | 필터 로드 → 패턴별 판정 + PASS/FAIL → 크기별 성능 표(3×3, 5×5, 13×13, 25×25) → 결과 요약 |
| `3` | 패턴 생성기 (보너스) | N 을 입력하면 N×N 십자가/X 패턴을 자동 생성해 보여주고, 판정과 성능을 확인 |
| `0` | 종료 | |

- 행렬 입력은 `0 1 0` 처럼 **공백으로 구분**합니다. (편의상 `010` 처럼 붙여 쓴 0/1 도 받아 줍니다.)
- 숫자 개수가 틀리거나 숫자가 아닌 값이 있으면 `입력 형식 오류: 각 줄에 3개의 숫자를 공백으로 구분해 입력하세요.` 를 출력하고 **그 줄을 다시** 입력받습니다. 한 줄씩 정해진 줄 수만큼 받기 때문에 행 수도 항상 3 으로 맞춰집니다.
- 모드 1 시작 시 `y` 를 누르면 패턴 생성기가 만든 십자가/X 를 필터 A/B 로 바로 씁니다. (보너스: 생성기 재활용)
- `Ctrl+C` 나 입력 끝(EOF)이 와도 튕기지 않고 안내 후 종료합니다.

**data.json 위치**: `main.py` 와 같은 폴더(프로젝트 루트)의 `data.json`

> ⚠️ 이 저장소의 `data.json` 은 **직접 만든 샘플**입니다 (`meta.note` 에 표시). 공식 `data.json` 은 Codyssey 미션 페이지 하단 첨부에서 내려받아 같은 자리에 덮어쓰면 됩니다. 샘플은 공식 스키마(`filters.size_N.cross/x`, `patterns.size_N_idx.input/expected`)를 그대로 따릅니다.

## 2. 구현 요약

### 데이터 구조
- N×N 행렬 = **2차원 리스트** (`matrix[행][열]`). `create_matrix`, `get_value`, `set_value` 로 만들고 읽고 씁니다.
- `check_matrix` 가 "정사각형인지, 모든 값이 숫자인지" 검사해서 크기 N 또는 오류 이유를 돌려줍니다.

### 라벨 정규화
- 프로그램 안에서는 표준 라벨 **`Cross`, `X`** 두 가지만 씁니다.
- `normalize_label()` 이 앞뒤 공백 제거 + 소문자 변환 후 표(`LABEL_MAP`)에서 찾습니다.
  - expected: `'+'` → `Cross`, `'x'` → `X`
  - 필터 키: `'cross'` → `Cross`, `'x'` → `X`
- 표에 없는 라벨(예: `'+_'`)은 `None` → 그 케이스는 FAIL + 사유 출력.
- 콘솔 출력과 PASS/FAIL 비교는 모두 표준 라벨 기준입니다.

### MAC 연산
```python
def mac(pattern, filter_matrix):
    n = len(pattern)
    total = 0.0
    for row in range(n):
        for col in range(n):
            total += pattern[row][col] * filter_matrix[row][col]
    return total
```
- 이중 for 문 → 정확히 **N×N = N² 번** 곱하고 더합니다.

### 동점 처리 정책 (epsilon)
- `abs(score_a - score_b) < 1e-9` 이면 **동점** → 모드 1 은 `판정 불가`, 모드 2 는 `UNDECIDED`.
- 모드 2 에서 `UNDECIDED` 는 expected(Cross/X)와 같을 수 없으므로 **FAIL** 로 집계합니다.

### 모드 2 케이스 단위 검증 (프로그램은 절대 멈추지 않음)
패턴마다 아래 순서로 검사하고, 걸리면 그 케이스만 `[FAIL] 사유` 로 처리한 뒤 다음 케이스로 넘어갑니다.
1. 키 형식 `size_{N}_{idx}` (정규식 `size_(\d+)_(\d+)`) → N 추출
2. `input`, `expected` 존재 여부
3. expected 라벨 정규화
4. `size_N` 필터 존재 여부
5. 패턴이 정사각 숫자 행렬인지 + **패턴 크기 == 필터 크기** 인지
6. MAC → epsilon 판정 → PASS/FAIL

### 성능 측정
- `time.perf_counter()` 로 **MAC 함수 호출 구간만** 잽니다 (입력/출력/파일 읽기 제외).
- 워밍업 1회 후 **10회 반복 평균(ms)**. 표에 `크기(N×N) / 평균 시간(ms) / 연산 횟수(N²)` 를 출력합니다.

### 보너스
- **1D 최적화**: `flatten()` 으로 2차원 → 길이 N² 1차원 리스트로 편 뒤 `mac_flat()` (for 문 1개)으로 계산. 성능 표에 2D/1D 를 같은 입력·같은 반복 횟수로 나란히 비교합니다. (펴는 시간은 측정에서 제외)
- **패턴 생성기**: `generate_cross(n)`, `generate_x(n)`. 모드 3 에서 N 입력 → 그림 출력/판정/성능, 모드 1 필터 자동 생성, 모드 2 성능 표의 입력(특히 data.json 에 없는 3×3)에 재활용.

## 3. 결과 리포트

### 3-1. 실행 결과 (샘플 data.json, 모드 2)

```
총 테스트: 8개
통과: 6개
실패: 2개
실패 케이스:
  - size_5_3: 크기 불일치 (패턴 13×13, 필터 size_5 = 5×5)
  - size_13_3: 동점(UNDECIDED) 처리 규칙에 따라 FAIL (|차이| = 5.55e-17 < 1e-09)
```

### 3-2. FAIL 케이스 원인 분석

실패 원인은 **① 데이터/스키마 문제, ② 로직 문제, ③ 수치 비교 문제** 세 갈래로 나눠서 진단했습니다.

1. **`size_5_3` → ① 데이터/스키마 문제.** 키는 `size_5`(5×5)라고 되어 있는데 실제 `input` 은 13×13 입니다. 키에서 뽑은 N 으로 필터를 고르기 때문에 5×5 필터와 13×13 패턴을 곱하게 되고, 그대로 계산하면 `IndexError` 로 프로그램이 죽습니다. 그래서 MAC 전에 `check_matrix` 로 크기를 먼저 비교하고, 다르면 그 케이스만 FAIL + 사유를 남긴 뒤 다음 케이스로 넘어가게 했습니다. 고치려면 프로그램이 아니라 **데이터**(키 이름 또는 input 크기)를 고쳐야 합니다.
2. **`size_13_3` → ③ 수치 비교 문제.** 십자가 칸에 0.1 과 0.2, X 칸에 0.3 이 들어 있습니다. 사람이 보면 0.1+0.2 = 0.3 으로 동점이지만, 컴퓨터는 실수를 2진수로 근사해서 저장하기 때문에 Cross 점수가 `0.30000000000000004` 가 됩니다. 그냥 `>` 로 비교했다면 Cross 가 "이겼다"고 잘못 판정해서 expected(+)와 우연히 맞아 PASS 가 나왔을 것입니다. epsilon(1e-9) 정책으로는 차이 5.55e-17 이 1e-9 보다 훨씬 작으므로 **동점(UNDECIDED)** 이 되고, 규칙에 따라 FAIL 입니다. 즉 이 FAIL 은 버그가 아니라 "애매하면 억지로 고르지 않는다"는 **정책이 의도대로 동작한 결과**입니다.
3. **라벨 문제(①)는 정규화로 0건이 되었습니다.** 샘플의 expected 는 `'+'`, `'x'` 이고 필터 키는 `'cross'`, `'x'` 입니다. 정규화 없이 문자열을 그대로 비교하면 판정 결과 `'Cross'` 와 expected `'+'` 가 달라서 PASS 6개가 **전부 FAIL** 이 됩니다. `normalize_label()` 로 둘 다 `Cross`/`X` 로 통일했기 때문에 라벨 때문에 실패한 케이스는 없습니다.
4. **② 로직 문제는 0건입니다.** 생성기로 만든 십자가/X 를 넣으면 항상 자기 필터 점수가 더 크게 나오는 것(예: 13×13 십자가 → Cross 25.0 / X 1.0)으로 MAC 과 판정 로직이 맞다는 것을 확인했습니다.
5. 참고로 키 형식 오류(`size__5_2`), 라벨 오타(`'+_'`), 해당 크기 필터 없음(`size_7_1`), 숫자가 아닌 값, 열 개수 불일치 같은 오류가 섞인 파일로도 시험했고, 모두 케이스 단위 FAIL 로 처리되며 프로그램이 멈추지 않았습니다.

### 3-3. 성능 표 (샘플 data.json 실행 결과, 평균/10회)

```
크기          2D 평균(ms)    1D 평균(ms)     연산 횟수(N²)
----------------------------------------------------
3×3            0.0005       0.0003             9
5×5            0.0009       0.0005            25
13×13          0.0047       0.0030           169
25×25          0.0165       0.0127           625
```
(측정 환경: Linux, Python 3.13 / 실행할 때마다, 컴퓨터마다 숫자는 조금씩 달라집니다.)

### 3-4. 시간 복잡도 분석 — 왜 O(N²) 인가

- MAC 은 N×N 칸을 **한 칸도 빼지 않고 한 번씩** 곱하고 더하므로 연산 횟수가 정확히 N² 입니다. 이중 for 문(바깥 N 번 × 안쪽 N 번)이 그 근거입니다. 그래서 시간 복잡도는 **O(N²)** 입니다.
- 측정값으로 확인: 13×13 → 25×25 에서 연산 횟수는 625 / 169 ≈ **3.7배**, 시간은 0.0165 / 0.0047 ≈ **3.5배** 로 거의 같은 비율로 늘었습니다.
- 생성기로 51×51 까지 재 보면 25×25 0.0172 ms → 51×51 0.0625 ms (**3.6배**), 연산 횟수는 2601 / 625 ≈ **4.2배** 로 역시 비슷하게 따라갑니다.
- 한 번 곱하고 더하는 데 드는 시간은 25×25 기준 0.0165 ms ÷ 625 ≈ **26 ns**, 51×51 기준 ≈ **24 ns** 로 거의 일정합니다. "연산 1번당 시간이 일정하다 = 전체 시간은 연산 횟수(N²)에 비례한다"는 뜻입니다.
- 반대로 3×3, 5×5 처럼 작은 크기는 연산 1번당 시간이 더 크게 나옵니다(3×3: 0.0005 ms ÷ 9 ≈ 55 ns). 함수 호출, 반복문 준비 같은 **고정 비용**이 상대적으로 크게 보이기 때문이라, 작은 N 에서는 N² 비율이 깔끔하게 안 맞습니다.
- 1D 버전은 인덱스 계산이 한 번뿐이라 조금 빠르지만(25×25: 0.0165 → 0.0127 ms) 여전히 N² 번 곱하므로 **복잡도는 똑같이 O(N²)** 입니다. 줄어드는 건 상수(한 번당 시간)뿐입니다.
- N 이 2배가 되면 시간은 약 4배가 됩니다. 실제 AI 모델은 수백×수백 필터를 수천 개 쓰기 때문에, CPU 처럼 하나씩 순서대로 계산하면 감당이 안 되고, 수많은 MAC 을 **동시에(병렬로)** 처리하는 NPU 가 필요한 이유가 바로 이것입니다.

