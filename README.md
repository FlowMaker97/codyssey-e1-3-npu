# 🧠 Mini NPU Simulator

> Codyssey E1-3 「AI가 계산하는 방식을 흉내 내는 작은 계산기 만들기」 미션 결과물

십자가(+)와 X 모양을 **숫자 배열(필터)** 로 정의하고, 입력 패턴과 필터를 **MAC(Multiply-Accumulate: 같은 위치끼리 곱해서 모두 더하기)** 연산으로 비교해 어떤 모양인지 판정하는 콘솔 프로그램입니다.
NumPy 같은 외부 라이브러리 없이 **파이썬 반복문으로 직접** MAC 을 구현했습니다.

## 1. 실행 방법

```bash
python3 --version      # Python 3.8 이상
python3 main.py
```

실행하면 모드를 고릅니다.

| 입력 | 모드 | 하는 일 |
|---|---|---|
| `1` | 사용자 입력 (3×3) | 필터 A, B 와 패턴을 한 줄씩 입력 → 저장 확인 → MAC 점수 / 연산 시간 / 판정(A·B·판정 불가) → 3×3 성능 표 |
| `2` | data.json 분석 | 필터 로드 → 패턴별 판정 + PASS/FAIL → 크기별 성능 표(3×3, 5×5, 13×13, 25×25) → 결과 요약 |
| `3` | 패턴 생성기 (보너스) | N 을 입력하면 N×N 십자가/X 패턴을 자동 생성해 보여주고, 판정과 성능을 확인 |
| `0` | 종료 | |

- 행렬 입력은 `0 1 0` 처럼 **공백으로 구분**합니다. (편의상 `010` 처럼 붙여 쓴 0/1 도 받아 줍니다.)
- 숫자 개수가 틀리거나 숫자가 아닌 값이 있으면 `입력 형식 오류: 각 줄에 3개의 숫자를 공백으로 구분해 입력하세요.` 를 출력하고 **그 줄을 다시** 입력받습니다. 한 줄씩 정해진 줄 수만큼 받기 때문에 행 수도 항상 3 으로 맞춰집니다.
- 모드 1 시작 시 `y` 를 누르면 패턴 생성기가 만든 십자가/X 를 필터 A/B 로 바로 씁니다. (보너스: 생성기 재활용)
- `Ctrl+C` 나 입력 끝(EOF)이 와도 튕기지 않고 안내 후 종료합니다.

**data.json 위치**: `main.py` 와 같은 폴더(프로젝트 루트)의 `data.json`

> ✅ 이 저장소의 `data.json` 은 Codyssey 미션 페이지에서 내려받은 **공식 data.json** 입니다. 스키마는 `filters.size_N.cross/x`, `patterns.size_N_idx.input/expected` 입니다.

## 2. 구현 요약

### 데이터 구조
- N×N 행렬 = **2차원 리스트** (`matrix[행][열]`). `create_matrix`, `get_value`, `set_value` 로 만들고 읽고 씁니다.
- `check_matrix` 가 "정사각형인지, 모든 값이 숫자인지" 검사해서 크기 N 또는 오류 이유를 돌려줍니다.

### 라벨 정규화
- 프로그램 안에서는 표준 라벨 **`Cross`, `X`** 두 가지만 씁니다.
- `normalize_label()` 이 앞뒤 공백 제거 + 소문자 변환 후 표(`LABEL_MAP`)에서 찾습니다.
  - expected: `'+'` → `Cross`, `'x'` → `X`
  - 필터 키: `'cross'` → `Cross`, `'x'` → `X`
- 표에 없는 라벨(예: `'+_'`)은 `None` → 그 케이스는 FAIL + 사유 출력.
- 콘솔 출력과 PASS/FAIL 비교는 모두 표준 라벨 기준입니다.

### MAC 연산
```python
def mac(pattern, filter_matrix):
    n = len(pattern)
    total = 0.0
    for row in range(n):
        for col in range(n):
            total += pattern[row][col] * filter_matrix[row][col]
    return total
```
- 이중 for 문 → 정확히 **N×N = N² 번** 곱하고 더합니다.

### 동점 처리 정책 (epsilon)
- `abs(score_a - score_b) < 1e-9` 이면 **동점** → 모드 1 은 `판정 불가`, 모드 2 는 `UNDECIDED`.
- 모드 2 에서 `UNDECIDED` 는 expected(Cross/X)와 같을 수 없으므로 **FAIL** 로 집계합니다.

### 모드 2 케이스 단위 검증 (프로그램은 절대 멈추지 않음)
패턴마다 아래 순서로 검사하고, 걸리면 그 케이스만 `[FAIL] 사유` 로 처리한 뒤 다음 케이스로 넘어갑니다.
1. 키 형식 `size_{N}_{idx}` (정규식 `size_(\d+)_(\d+)`) → N 추출
2. `input`, `expected` 존재 여부
3. expected 라벨 정규화
4. `size_N` 필터 존재 여부
5. 패턴이 정사각 숫자 행렬인지 + **패턴 크기 == 필터 크기** 인지
6. MAC → epsilon 판정 → PASS/FAIL

### 성능 측정
- `time.perf_counter()` 로 **MAC 함수 호출 구간만** 잽니다 (입력/출력/파일 읽기 제외).
- 워밍업 1회 후 **10회 반복 평균(ms)**. 표에 `크기(N×N) / 평균 시간(ms) / 연산 횟수(N²)` 를 출력합니다.

### 보너스
- **1D 최적화**: `flatten()` 으로 2차원 → 길이 N² 1차원 리스트로 편 뒤 `mac_flat()` (for 문 1개)으로 계산. 성능 표에 2D/1D 를 같은 입력·같은 반복 횟수로 나란히 비교합니다. (펴는 시간은 측정에서 제외)
- **패턴 생성기**: `generate_cross(n)`, `generate_x(n)`. 모드 3 에서 N 입력 → 그림 출력/판정/성능, 모드 1 필터 자동 생성, 모드 2 성능 표의 입력(특히 data.json 에 없는 3×3)에 재활용.

### 3-1. 실행 결과 (공식 data.json, 모드 2)

```

통과: 3개
실패: 3개
실패 케이스:
  - size_5_1: 동점(UNDECIDED) 처리 규칙에 따라 FAIL (|차이| = 1.11e-16 < 1e-09)
  - size_13_2: 동점(UNDECIDED) 처리 규칙에 따라 FAIL (|차이| = 2.66e-15 < 1e-09)
  - size_25_1: 동점(UNDECIDED) 처리 규칙에 따라 FAIL (|차이| = 1.78e-15 < 1e-09)
```

| 케이스 | Cross 점수 | X 점수 | 판정 | expected | 결과 |
|---|---|---|---|---|---|
| size_5_1 | 0.9 | 0.8999999999999999 | UNDECIDED | X | FAIL (동점 규칙) |
| size_5_2 | 8.9 | 0.1 | Cross | Cross | PASS |
| size_13_1 | 0.3 | 14.700000000000008 | X | X | PASS |
| size_13_2 | 7.499999999999997 | 7.5 | UNDECIDED | Cross | FAIL (동점 규칙) |
| size_25_1 | 4.9 | 4.899999999999999 | UNDECIDED | X | FAIL (동점 규칙) |
| size_25_2 | 52.9 | 0.1 | Cross | Cross | PASS |

### 3-2. FAIL 케이스 원인 분석

실패 원인은 **① 데이터/스키마 문제, ② 로직 문제, ③ 수치 비교 문제** 세 갈래로 나눠서 진단했습니다.

1. **FAIL 3건 모두 ③ 수치 비교 문제입니다.** 세 케이스 모두 Cross 점수와 X 점수가 사람이 보기엔 같은 값입니다(0.9 vs 0.9, 7.5 vs 7.5, 4.9 vs 4.9). 그런데 컴퓨터는 0.1 같은 실수를 2진수로 근사해서 저장하기 때문에, 여러 번 곱하고 더하는 동안 아주 작은 오차가 쌓여 `0.8999999999999999`, `7.499999999999997` 처럼 됩니다.
2. 이때 그냥 `>` 로 비교했다면 오차 때문에 한쪽이 "이겼다"고 판정됐을 것입니다. 예를 들어 size_5_1 은 Cross 가 0.9 로 미세하게 커서 Cross 로 판정되고, expected(X)와 달라 결국 FAIL 이 됩니다. 즉 오차에 따라 결과가 우연히 맞거나 틀리는, 믿을 수 없는 판정이 됩니다.
3. 그래서 `abs(a - b) < 1e-9` 이면 **동점(UNDECIDED)** 으로 보는 epsilon 정책을 썼고, 세 케이스의 차이(1.11e-16, 2.66e-15, 1.78e-15)는 1e-9 보다 훨씬 작으므로 동점이 되어 규칙대로 FAIL 입니다. 이 FAIL 은 버그가 아니라 **"애매하면 억지로 고르지 않는다"는 정책이 의도대로 동작한 결과**입니다. 이 패턴들은 두 필터와 똑같이 닮아 있어서, 데이터 자체가 Cross/X 를 구분할 수 없는 경우라고 봅니다.
4. **① 데이터/스키마 문제는 0건입니다.** 6개 케이스 모두 키(`size_N_idx`)의 N 과 실제 input 크기가 일치했고, 필터도 size_5/13/25 가 모두 정상 로드되었습니다. 라벨도 `normalize_label()` 로 Cross/X 로 통일한 뒤 비교했기 때문에 라벨 표기 차이로 실패한 케이스는 없습니다.
5. **② 로직 문제는 0건입니다.** 점수 차이가 분명한 케이스(size_5_2, size_13_1, size_25_2)는 모두 큰 점수 쪽으로 정확히 판정되어 PASS 했고, 생성기로 만든 십자가/X 를 넣으면 항상 자기 필터 점수가 더 크게 나오는 것으로 MAC 과 판정 로직이 맞다는 것을 확인했습니다.
6. 참고로 키 형식 오류(`size__5_2`), 라벨 오타, 해당 크기 필터 없음, 숫자가 아닌 값, 크기 불일치 같은 오류가 섞인 파일로도 시험했고, 모두 케이스 단위 FAIL 로 처리되며 프로그램이 멈추지 않았습니다.

```
----------------------------------------------------
3×3            0.0015       0.0008             9

```

### 3-4. 시간 복잡도 분석 — 왜 O(N²) 인가

- MAC 은 N×N 칸을 **한 칸도 빼지 않고 한 번씩** 곱하고 더하므로 연산 횟수가 정확히 N² 입니다. 이중 for 문(바깥 N 번 × 안쪽 N 번)이 그 근거입니다. 그래서 시간 복잡도는 **O(N²)** 입니다.
- 측정값으로 보면 3×3 → 25×25 에서 연산 횟수는 625 / 9 ≈ **69배**, 2D 시간은 0.0366 / 0.0015 ≈ **24배** 늘었습니다. 크기가 커질수록 시간이 함께 커지는 경향은 분명합니다.
- 다만 비율이 N² 와 딱 맞지는 않습니다. 측정 시간이 0.001~0.04 ms(마이크로초 단위)로 매우 짧아서, 함수 호출·반복문 준비 같은 **고정 비용**과 OS 스케줄링 같은 **측정 잡음**이 상대적으로 크게 섞이기 때문입니다. 3×3 에서 연산 1번당 시간은 0.0015 ms ÷ 9 ≈ 167 ns 로, 25×25 의 0.0366 ms ÷ 625 ≈ 59 ns 보다 훨씬 큽니다. 작은 N 일수록 고정 비용의 비중이 크다는 뜻입니다.
- 1D 버전은 인덱스 계산이 한 번뿐이라 대체로 조금 빠르지만(13×13: 0.0192 → 0.0084 ms), 25×25 에서는 오히려 0.0427 ms 로 느리게 나왔습니다. 이 정도 차이는 측정 잡음 범위로 보이며, 1D 도 결국 N² 번 곱하므로 **복잡도는 똑같이 O(N²)** 입니다. 줄어드는 건 상수(한 번당 시간)뿐입니다.
- N 이 2배가 되면 연산 횟수는 4배가 됩니다. 실제 AI 모델은 수백×수백 필터를 수천 개 쓰기 때문에, CPU 처럼 하나씩 순서대로 계산하면 감당이 안 되고, 수많은 MAC 을 **동시에(병렬로)** 처리하는 NPU 가 필요한 이유가 바로 이것입니다.
